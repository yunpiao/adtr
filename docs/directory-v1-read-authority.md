## Reproduced behavior and existing contract

`directory-api-contract.md` requires current identity and read permissions for
observations and actor-bound receipt/task recovery, with no automatic write
replay. The actual API parsed JSON before handling failed HTTP status. Rejected
JSON called `invalid()`, producing invalid_response with status0. `useTaskRead`
recognizes session errors by code and retries invalid_response after two seconds.

Actual Observation plus actual API under synthetic transport showed JSON401
unauthenticated: one GET and one session callback; HTML401: two GETs in2.2seconds
and no callback. HTML403 likewise retried and showed generic malformed-result
text instead of the permission message. No old data or authorization bypass was
observed. This is controlled malformed-response evidence, not a claim that the
normal backend or a production gateway generated HTML.

Search-length and pagination hypotheses were explicitly excluded: the relevant
asset search contracts use UTF-16 units, and directory-v1 already binds page,
size, observation pin and empty-state semantics. Neither is changed here.

## Narrow repair and deliberate recovery boundaries

Only the JSON rejection callback in `directory-api.ts` changes. If and only if
this is a GET and the response is unsuccessful, HTTP401/403 map to existing
unauthenticated/forbidden errors with those status codes. This restores current
session handling and permission text and prevents treating known read-authority
failures as transient malformed content. A generic403 does not force logout.
Structured JSON password-change errors keep their existing session behavior.

The `body === undefined` discriminator already selects GET versus POST. It is
necessary to exclude sync/cancel mutations: an unreadable POST response remains
invalid_response/status0 and uncertain, since a task or cancellation may have
committed. No new intent/key, retry POST, grant or proof is generated by this fix.
Removing that guard would wrongly turn uncertain writes into definitive denials.

Malformed404 deliberately remains invalid_response/status0. Recovery's existing
structured404/not_found branch can display an explicit same-key retry form;
this candidate does not infer that condition from a failed body decode. The
original intent stays saved, no POST runs automatically, and the existing
structured404 warning says a missing receipt does not prove submission failed.
Both behaviors have direct Workspace controls in the new tests.

Parsed JSON policy is unchanged, including exact error-object shape, arbitrary
string codes, password/tenant errors and other status meanings. Other malformed
statuses, successful DTO and actor-header checks, network/abort behavior and
all UI/shared hooks remain unchanged. There is no added setting, dependency,
backend capability or change to v2/v3/v4 readers.

The fallback is necessary when the known failed read has an unreadable body;
without it the original callback/retry defect returns. Its intended side effect
is to stop automatic retries for401/403 reads. Users can explicitly refresh
once session/access is restored. Existing transient-read retry behavior remains
for other malformed responses.
