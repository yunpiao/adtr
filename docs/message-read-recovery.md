# F40 单条已读与原操作恢复

Refs [#107](https://github.com/yunpiao/adtr/issues/107)、[#50](https://github.com/yunpiao/adtr/issues/50)，AD-F-158/159 有界 UI 切片。基线 main `4aa9eedbfa0061c731031b749b350238a8337e11`，复用 PR104 运行时、PR106 固定消息查询；不修改 schema、服务端权限、消息来源或批量/取消政策。

## 身份、查询与单条写入

当前 `tasks.readable` 和五条精确消息操作检查共同约束页面；个人已读不是后台任务写入，不要求 `tasks.writeable`、密码或 MFA。服务端仍在每个请求核对真实会话、当前授权与 Origin/CSRF。页面仅对当前固定结果内查询时未读行提供单条按钮；提交 JSON 只有原 `resultId`、`messageId`、`operationId`，没有客户端用户、租户、首次时间、权限或计数覆盖。

成功收据严格匹配三个原标识、UTC 时间及单条进度：Target=Processed=1，NewlyRead+AlreadyRead=1，Failed=Remaining=0。损坏字段、错误目标、部分进度不能显示成功。首次时间由服务端实际持久化提供；重放返回原收据，不合成新的统计。

写入成功后原查询结果完全保持：成员、序号、阅读状态、首次已读列和 counts 都是查询时快照。成功面板单独展示已核实操作与首次时间，并明确要求点击“确认查询”创建新快照后才能看到新阅读状态/统计。草稿和新查询不会替换原操作中的 resultId。固定结果过期或清除不影响历史收据入口。

## 未知提交状态机

1. 用户点击单条已读，先检查该账户未决记录，再生成 operationId，并将完整三标识写入本机存储、回读核实。失败时不发出请求；同步锁阻止重复点击
2. 首次 POST 成功仅在收据校验通过后确认。网络中断、无效 JSON、状态错误与晚响应均不等于失败或取消；未决意图保持，不能另生替代 operationId
3. 恢复进入、重新登录、StrictMode、storage/focus 事件都不自动 GET 或 POST。用户点击“查询原操作结果”，在当前权限下读取本人 receipt
4. 只有严格 `404/not_found` 的收据查询才显示“重放原操作”。这个状态实际表示本次没有查到成功收据，不能证明先前未提交或没有在途提交
5. 用户选择重放时再次先 GET 原 receipt。查到则确认，不写入；再次明确 not_found 后回读持久化原意图，再 POST 原三标识。任何其他错误都返回待核对状态；不利用旧快照过期来跳过收据查证
6. 新会话重建 UI，任何原 replayable 状态重置为 unknown；跨用户组件重建，不展示或重放另一账户记录。旧 cookie 与撤权由服务端拒绝。401/403/强制改密清私有页面及能力，保留非敏感未知意图供本人以后恢复
7. 离开、Back、刷新或关闭页面只结束当前等待，不取消、撤销或删除操作。迟到响应不能在新身份或卸载后确认/清记录

没有“取消未知操作”按钮。拒绝重放、目标冲突或快照过期仍保留原意图，继续提供收据核对；尚未取得可信成功收据时不声称已经提交、失败或撤销。

## 本机记录与副作用

`localStorage` 按账户 ID、编码用户名和 operationId 独立键保存 `{version,owner,username,input}`；input 严格只有三个标识。它用于浏览器刷新、关闭标签再打开及重新登录后保持原操作，未启用可可靠写入的存储时该写入功能必须停用，否则可能丢失幂等键。不会保存 cookie、CSRF、密码、MFA、消息正文、query 结果、收据或时间。原 ID 是恢复定位所需的有限非秘密数据，不授予任何服务端访问能力。

独立 operation 键避免两个标签覆盖彼此未知记录；storage/focus 仅合并恢复记录，创建新操作前再次检查磁盘。一个页面同时只执行一个已读/收据请求，未知记录存在时阻止新的单条提交。不同标签同时起步仍可能分别生成操作；后端个人首次已读与各自幂等收据保证一致，两个原记录都可单独核对。

成功收据核实后尝试只删除匹配的本机意图；删除失败明确说明并可再次核对原收据。损坏/无法读取存储拒绝新写，不静默丢未知意图。清除浏览器站点数据、隐私模式退出或换浏览器会丢本机恢复索引，服务端成功收据/首次已读仍保留；本切片没有服务端操作历史列表。关闭标签保留依赖正常持久存储，不承诺浏览器外备份。
