# Container memory observations (engineering #117)

Refs #14, AD-F-196/200. This additive slice is read-only runtime cgroup accounting, not resource configuration or full product acceptance. The API still registers only local-api. No database schema change is needed: observations use the existing JSONB snapshot and its tenant/instance/timestamp key. Schema 18 remains unchanged by this slice.

## Sources and meaning

- Existing `memory`, `ram_basic` and `info.status.memoryUsagePercent` retain Linux kernel-visible `MemTotal-MemAvailable` semantics. Host totals are never used as a fallback cgroup limit.
- New optional `snapshot.containerMemory` records metadata, decimal-string `usageBytes`/`limitBytes`, nullable numeric `percent`, `limitState` (finite/unlimited/unknown), and `hierarchy=visible`. New successful accounting samples also include opaque `sourceID` for continuity, optional on historical JSON. Scope is `runtime_cgroup`; source is cgroup_v2, cgroup_v1 or unknown cgroup discovery.
- Linux discovers the current process membership through `/proc/self/cgroup` and filesystem mapping through `/proc/self/mountinfo`, including mount-root offsets and private cgroup namespace paths. It rejects traversal, duplicate relevant membership, ambiguous mounts and overlong inputs. It reads fixed memory files only, never accepts client paths, shells out, writes limits or changes security settings. Reads are bounded to 1 MiB, ancestry to 128 levels, and membership is rechecked to discard migrations during a sample.
- v2 usage is `memory.current`; the visible ceiling is the minimum finite `memory.max` from the current group through the mounted hierarchy. `max` is unbounded at that level. v1 uses `memory.usage_in_bytes` and `memory.limit_in_bytes` with enabled hierarchy at every visible ancestor; the 64-bit kernel unlimited sentinel is recognized. v1 usage is kernel accounting with its documented batching/fuzz, not an exact process RSS.
- The finite ratio is current group usage / smallest visible ancestor ceiling × 100. It can exceed 100 during kernel reclaim/transitions and is never clamped. A shared ancestor also accounts siblings. Hidden ancestors, shared competition, swap, memory.high pressure and OOM risk are not captured by this ratio. A visible finite limit is not guaranteed available headroom or proof of whole-host/container health. Raw internal cgroup paths and OS errors are not exposed.
- A distinct v2 hierarchy-root ancestor may lack memory.max/current by kernel design; sampling only accepts that absence when both are ENOENT, the mount root is / and cgroup.controllers confirms memory. The sampled namespace leaf is never exempted. Other missing controller files, unreadable ancestors, malformed values or ambiguous namespace mappings remain explicitly unavailable. Discovery does not guess a container identity from hostname or assume proc RAM is container RAM. Unsupported platforms return unsupported_platform; Windows and multi-node support remain open.

## Availability and persistence

Finite valid measurements are available with usage, limit and ratio. Unlimited observations retain usage but have unavailable/unlimited and null limit/ratio. Unknown/unreadable/corrupt observations have null values and stable reason codes. Old JSON snapshots without the additive field remain readable and mean no cgroup observation. Failed samples do not carry forward earlier values. A legal zero quota has no calculable denominator and returns zero_limit, not a fabricated ratio.

Sampling remains every 15 seconds; current evidence expires after 45 seconds. Stale/clock-skew current snapshots may be shown as historical context but cannot count as healthy. Cgroup measurement availability is separately assessed from kernel-visible sampler availability; unknown/unlimited/missing evidence never yields a healthy cgroup dependency. A finite ratio reaching 100 reports visible_limit_reached, without claiming a configurable alert policy.

`graphType=container_ram` reuses the history endpoint and its strict instance, time and installation-owner permissions. No storageId is accepted. History reads only real persisted finite observations, validates their source/metadata/byte arithmetic, and emits explicit gaps. `segments` marks the first real point and each changed/missing source identity, source version or finite denominator. Segment boundaries are not missing observations; aggregate statistics describe the observed ratios across their explicitly identified segments. Old/unlimited/unavailable samples never become zero points. Range, 5760-point cap, statistics and restart persistence follow existing history rules. Corrupt stored finite metrics fail closed with invalid_stored_observation. PostgreSQL timestamps normalize to microseconds while snapshot JSON retains nanoseconds: history validates the normalized row time and the metric against the original JSON timestamp; a real-DB regression asserts both representations.

Source identity hashes the fixed boot ID, cgroup namespace identity, opened directory device/inode and change time, with pre/post rechecks. Raw identities/paths are not exposed. This is a continuity token for the currently observable kernel source, not a permanent Docker/container identifier. Inode reuse, namespace replacement, directory changes, inaccessible identity sources or process migration cannot establish permanent identity; observed changes create a new segment, sampling races fail unavailable, and missing legacy identity starts an independent segment for every point. No Docker socket or elevated permissions are used.

## Configuration and impact

There is no new production configuration parameter or required deployment change. Removing this additive metric would remove cgroup observations/history while retaining kernel-visible RAM. Sampling adds bounded read-only proc/cgroup metadata and identity I/O every 15 seconds. Existing persisted snapshots are forward-compatible at the database level; older applications may ignore the extra JSON field and do not offer container_ram queries.

`ADTR_TEST_CGROUP_LIMIT` is test-harness-only and required solely for the cgroupdocker-tagged test, not production. It states the isolated Docker limit expected by the test; without it that test fails instead of skipping. Docker `--memory=268435456` applies only to a uniquely labelled temporary test container and demonstrates a real 256 MiB quota; the second test omits it and verifies actual visible accounting rather than assuming unlimited parent resources. Neither changes host cgroups. Both use a private cgroup namespace, verify the raw kernel limit against the reported finite/unlimited state, restart the same container and clean up only verified test identities.
